## 1. Why this project exists

Feeding India serves meals to lakhs of children in schools and Anganwadis every day. Tracking about 1.4 lakh meals a day, without failing on any day, needs a backend that is reliable, can tell when data is wrong or missing, and gives operators a clear picture each morning.

MealTrack is a small but realistic version of that system:

- Every feeding centre reports how many meals it served today.
- The backend accepts reports in two ways: a structured form/API call, and a **messy free-text message** (like a WhatsApp message) that an LLM converts into a structured report.
- The system catches duplicates, impossible numbers, missing reports and sudden drops or spikes, and raises alerts.
- A dashboard shows today's total meals, reporting coverage, and open alerts by district and centre.

**Important honesty rule:** all data in this project is **synthetic**, generated by a seed script. This project is not affiliated with Feeding India and must not claim real numbers. State this clearly in the final README.

The skills this project shows: reliable backend design, data validation, idempotency, anomaly detection, LLM use with a safe fallback, tests, Docker, and a deployed demo.

## 4. Architecture

```
 Dashboard (React) ──► REST API (Spring Boot) ──► PostgreSQL
                            │
                            ├── ReportService (validate, idempotent upsert)
                            ├── ParseService ──► LlmClient (Claude/Gemini) ──► on failure: RuleBasedParser
                            ├── AnomalyService (runs after each report and on a schedule)
                            └── SummaryService (aggregates for the dashboard)
```

Package layout (under `com.parth.mealtrack`):

```
config/        // properties, CORS, API key filter
domain/        // JPA entities
repo/          // Spring Data repositories
service/       // ReportService, ParseService, AnomalyService, SummaryService
llm/           // LlmClient (interface), ClaudeClient / GeminiClient, RuleBasedParser
web/           // controllers, DTOs, exception handler

seed/          // SeedDataRunner (profile "seed")
```

## 6. REST API

Base path `/api`. All write endpoints need header `X-API-Key` (value from env `MEALTRACK_API_KEY`). Reads are open.

### 6.1 Centres
- `GET /api/centres?district=&active=&page=&size=` → paged list
- `POST /api/centres` → create a centre (validated)
- `GET /api/centres/{id}`

### 6.2 Reports
- `POST /api/reports`
  ```json
  { "centreCode": "GGN-0001", "date": "2026-11-22", "mealsServed": 180 }
  ```
  - 201 if new, 200 if an existing report for that centre and date was updated.
  - 400 for invalid input (negative meals, future date, unknown centre, inactive centre).
- `POST /api/reports/parse`
  ```json
  { "centreCode": "GGN-0001", "message": "aaj 180 bachchon ko khana diya, 20 absent the" }
  ```
  - Parse the message into `{ date, mealsServed }`. Date defaults to today if the message has none.
  - Response includes `mealsServed`, `date`, `parseMethod` (`LLM` or `RULES`) and `confidence` (`HIGH`/`LOW`).
  - If confidence is `LOW`, do **not** save the report. Return 422 with a clear message, and create a `PARSE_UNCERTAIN` alert so a human checks it.
  - If confidence is `HIGH`, save it through the same validation and idempotency as `POST /api/reports`.
- `GET /api/reports?centreCode=&from=&to=` → history

### 6.3 Alerts
- `GET /api/alerts?status=OPEN&type=&district=&date=`
- `PATCH /api/alerts/{id}/resolve`

### 6.4 Summary (for the dashboard)
- `GET /api/summary/daily?date=2026-11-22` →
  ```json
  {
    "date": "2026-11-22",
    "totalMeals": 138420,
    "centresActive": 1000,
    "centresReported": 962,
    "coveragePercent": 96.2,
    "openAlerts": 31,
    "byDistrict": [ { "district": "Gurugram", "meals": 12400, "reported": 80, "total": 85 } ]
  }
  ```
- `GET /api/summary/trend?days=30` → total meals per day for the chart.

### 6.5 Errors
One global `@RestControllerAdvice` returning a consistent body: `{ "timestamp", "status", "error", "message", "path" }`. Never return stack traces.

## 7. Validation and idempotency rules

1. `mealsServed` must be between 0 and `expected_meals * 2` for acceptance. Above `expected_meals * 1.5` is saved but raises `EXCEEDS_CAPACITY`. Above `expected_meals * 2` is **rejected** (400) as a probable typo.
2. `date` cannot be in the future. Reports older than 7 days are rejected (late corrections need an admin, out of scope).
3. A second report for the same centre and date **updates** the row (keep `created_at`, change `updated_at`), and the anomaly check re-runs on the new value.
4. Unknown or inactive centre code → 400 with a clear message.
5. All writes are inside a transaction. Handle the race of two simultaneous reports with the unique constraint (catch the violation and retry as an update). Write a test for this.

## 8. Anomaly detection rules

Implement in `AnomalyService` as small, separately testable rule classes. Each rule returns zero or one alert. Rules for a report on date D for a centre:

| Rule | Condition | Severity |
|---|---|---|
| `ZERO_MEALS` | meals_served == 0 on a day the centre is active | MEDIUM |
| `SUDDEN_DROP` | meals_served < 60% of the centre's average of the last 7 reported days (need at least 3 days of history) | HIGH if < 40%, else MEDIUM |
| `SPIKE` | meals_served > 140% of that 7-day average (same history requirement) | MEDIUM |
| `EXCEEDS_CAPACITY` | meals_served > 1.5 × expected_meals | MEDIUM |
| `MISSING_REPORT` | no report by the cutoff time (default 14:00 IST) for an active centre | LOW at first, HIGH if the centre also missed the previous day |

Details:
- `MISSING_REPORT` is created by a scheduled job (`MissingReportJob`, Spring `@Scheduled`, cron from config). The job must be **idempotent** (running it twice creates no duplicate alerts, thanks to the unique constraint).
- When a late report arrives for a missing centre, automatically mark that `MISSING_REPORT` alert `RESOLVED`.
- Alert `message` must include the numbers, e.g. `"Reported 70 meals; 7-day average is 182 (38%)."`
- All thresholds go in `application.yml` under `mealtrack.anomaly.*` so they are configurable. Do not hard-code them.

## 9. LLM parsing with a safe fallback (the "AI-native" part)

Goal: turn messy messages like these into `{ date, mealsServed }`:

- `"aaj 180 bachchon ko khana diya"`
- `"Meals served today: 1,250"`
- `"served 95 kids, 12 absent, total enrolled 107"` (answer is 95, not 12 or 107)
- `"khana nahi bana aaj, gas khatam"` (no meals → 0, but confidence LOW so a human checks)

Design:

1. `LlmClient` interface: `ParsedReport parse(String message, LocalDate today)`.
2. Implementation calls the provider with a **strict prompt** that asks for JSON only: `{"mealsServed": <int|null>, "date": "<YYYY-MM-DD|null>", "confidence": "HIGH|LOW"}`. Use a short timeout (5 s) and a maximum of 2 retries with backoff.
3. **Never trust the LLM output.** After parsing the JSON, run the same validation as section 7. If JSON is invalid, a field is missing, or the number fails validation, treat it as an LLM failure.
4. **Fallback:** on timeout, API error, missing API key, or invalid output, use `RuleBasedParser` (regex: find numbers near keywords such as `served`, `meals`, `khana`, `bachche`, `kids`, `students`; ignore numbers near `absent`, `enrolled`, `total`). If the rule-based parser finds exactly one confident number, confidence is HIGH; otherwise LOW.
5. The response and the DB row record `parse_method` (`LLM` or `RULES`).
6. The app must **work fully with no API key** (rules only). This is important for the demo and for tests.
7. Log each parse (method, success/failure, latency). Do not log API keys.
8. Tests: mock `LlmClient` to simulate success, timeout, invalid JSON, and wrong number; assert the fallback behaviour. Include a table-driven test for `RuleBasedParser` with at least 15 example messages (English, Hinglish, with commas, with absent/enrolled distractors).

## 10. Synthetic data (seed)

Create `SeedDataRunner`, run only with Spring profile `seed` (or `docker compose run seed`).

- Generate **1,000 centres** across 8 fictional-looking districts (use real Haryana/Delhi district names for realism but do not claim real centres): 60% schools, 40% Anganwadis.
- `expected_meals`: schools 80–400, Anganwadis 25–60. Set a random seed so the data is reproducible.
- Generate **30 days of history** with realistic noise (±8%), lower counts on Saturdays, and **no reports on Sundays**.
- Randomly skip about 3% of reports (these become missing reports).
- Inject known anomalies for today's demo so the dashboard is interesting: 10 sudden drops, 5 spikes, 5 zero-meal centres, 40 missing reports.
- Total for a normal weekday should land near **1.4 lakh meals** (tune the centre sizes to hit this). Mention in the README that this number is chosen to mirror the scale described in the hiring post, and that data is synthetic.
